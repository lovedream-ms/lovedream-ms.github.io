Linux设备驱动模型

Linux设备驱动模型是内核中管理和组织硬件设备的核心框架，它通过抽象化硬件，为驱动程序提供统一接口，简化了设备识别、驱动匹配和系统管理的复杂性。该模型基于总线、设备、驱动和类四大核心组件构建，通过sysfs文件系统向用户空间公开设备信息。理解设备驱动模型对嵌入式Linux和驱动开发至关重要，它使得内核能够高效地识别硬件、加载匹配的驱动程序，并提供统一的设备访问接口。

两个视角：四大核心组件+文件系统视角

设备驱动模型的基本架构

Linux设备驱动模型的核心是总线、设备、驱动和类四个组件。总线是连接设备和驱动的桥梁，负责管理和协调设备与驱动的匹配过程。设备代表物理硬件单元，驱动是控制设备的软件模块，而类则对功能相似的设备进行逻辑归类，提供统一接口。

总线（Bus）

数据结构：struct bus_type

作用：作为设备和驱动的匹配桥梁（如PCI、USB、I2C等总线）。

常见总线如下：

总线类型 示例 描述
实体总线 PCI、USB、I2C、SPI 物理存在于硬件电路中，具有枚举机制
虚拟总线 platform、serio、amba 无物理总线控制器，依赖设备树或手动注册

每种总线下均包含两个子目录：devices/：包含挂接的所有设备实例，drivers/：包含注册到总线的驱动程序

所有的总线类型无论是虚拟总线还是实际物理总线创建后都会被挂载到/sys/bus下，每个总线类型内部包含了一个Kobj用于指向父目录并未子目录提供挂载点，两个Kset指针分别指向device和driver子目录，在device和driver目录下包含了该总线下挂载的所有驱动和设备。

每一总线结构体内部都包含了match和probe两个函数指针，match负责设备和驱动间的匹配检验，probe负责在匹配成功后对新加入的设备或总线进行挂载。

实践如下

设备（Device）

数据结构：struct device 包含设备名称、所属总线、设备号等信息

作用：描述一个硬件或虚拟设备（如传感器、USB设备）

设备名称、唯一标识（如设备树中的 compatible 属性）
所属总线、父设备（用于构建设备树层次）

设备的代码含义是对Kobject的一个二次封装，都会挂载在/sys/devices目录下。在每一个设备路径下都会有一个subsystem软连接文件指向设备挂载的总线目录，相对的在创建一个设备后也会在对应的总线下创建一个软连接文件指向当前的设备路径。

设备挂载到对应驱动后对应的驱动设备链表会增加一个新的设备节点，并尝试匹配，当新的驱动挂载后会遍历该设备链表尝试匹配。

驱动（Driver）

作用：实现设备的具体操作（如读写寄存器、中断处理）。

数据结构：struct device_driver（基础驱动）
关键方法：

驱动的基本结构也是对一个Kobj的二次封装，所有的驱动文件都会挂载到对应总线的drivers目录下。在挂载到总线后driver会调用总线的match函数进行配对，当匹配到对应的设备后会将当前driver加入到当前总线的驱动链表的末尾。

总线内部包含一个probe函数，当设备挂载到总线会调用该probe函数，当驱动挂载后驱动内部也包含一个probe函数，两个probe函数存在优先级的关系，默认会先执行总线的probe函数，当总线的probe没有实现（函数指针为空）时，才会执行驱动中的probe函数，当然我们也可以在总线的probe函数中按照相应条件手动挂载驱动的probe。

类（Class）

数据结构：struct class。

作用：将具有相似功能的设备分组（如所有输入设备归属 input 类）从而提供标准化的接口

这四个组件通过kobject/kset层次结构组织成一个逻辑树。总线注册后，在/sys/bus目录下创建一个子目录；设备注册后，在/sys/devices目录下创建表示其层次结构的目录；驱动注册后，在总线的drivers目录下创建一个子目录；类则在/sys/class目录下创建一个目录。

总线的作用与实现机制

总线是设备驱动模型的核心枢纽，它维护设备和驱动的注册列表，并通过匹配（match​）和探测（probe​）机制实现设备与驱动的自动关联。总线的match函数是设备驱动匹配的关键，它根据特定总线的匹配规则（如PCI的厂商ID和设备ID，Platform的名称或兼容性字符串）判断设备与驱动是否兼容。

以PCI总线为例，其匹配过程如下：设备注册时，内核会读取PCI配置空间中的厂商ID和设备ID；驱动注册时，驱动程序会提供一个id_table​数组，列出支持的设备ID。当驱动注册到PCI总线时，总线会遍历设备链表，调用match函数检查每个设备的ID是否与驱动的id_table​匹配。匹配成功后，总线会调用驱动的probe函数，完成设备初始化和绑定。

Platform总线（Linux虚拟总线）的匹配规则略有不同，它优先通过设备树中的compatible​属性进行匹配，其次比较设备和驱动的名称。如果驱动提供了id_table，则会先进行ID匹配；否则直接比较名称是否相同。无论是先注册设备还是先注册驱动，总线都会自动触发匹配过程，确保设备与驱动正确绑定。

总线的probe函数负责在匹配成功后执行设备初始化操作。对于PCI总线，__pci_device Probe函数会调用驱动的probe函数；对于Platform总线，platform Probe函数同样会执行驱动的初始化逻辑。设备与驱动的绑定关系通过驱动指针（device->driver）和设备列表（driver->bus->devices）来维持，形成一个双向关联的结构。

设备与驱动的注册流程

设备注册是驱动模型的首要步骤。设备注册通常通过device_add函数完成，该函数会将设备添加到总线的设备链表中，并触发总线的匹配机制。具体流程如下：

  1. 创建设备结构体：设备驱动程序需要定义一个struct device​实例，指定设备名称、所属总线等信息。
  2. 初始化设备对象：调用device_initialize​函数初始化设备的kobject、引用计数和锁机制。
  3. 添加设备到总线：调用device_add​函数将设备添加到总线，触发总线的匹配过程，寻找已注册的匹配驱动。
  4. 创建设备节点：如果设备需要用户空间访问，驱动程序可以调用device Create​函数在类目录下创建设备节点。

驱动注册则通过driver Register函数完成，将驱动添加到总线的驱动链表中，并触发匹配机制。流程如下：

  1. 创建驱动结构体：驱动程序定义一个struct device Driver​实例，包含驱动名称、匹配函数、探测函数等。
  2. 注册驱动到总线：调用driver Register​或总线专用注册函数（如platform Driver Register​），最终触发bus Add Driver​函数。
  3. 匹配设备与驱动：bus Add Driver​调用driver Attach​函数，遍历总线上的设备链表，调用总线的match函数进行匹配。
  4. 执行probe函数：匹配成功后，调用驱动的probe函数完成设备初始化，建立设备与驱动的绑定关系。

设备注册和驱动注册的顺序不影响最终匹配结果，无论是先注册设备还是先注册驱动，总线都会在注册时遍历现有对象列表，寻找匹配。这种机制使得热插拔设备能够与内核中已加载的驱动自动关联，也使得驱动能够在设备存在时立即绑定。

sysfs 文件系统与设备模型映射

Linux设备模型通过sysfs文件系统向用户空间公开设备信息，sysfs是一个虚拟文件系统，通常挂载在/sys​目录下。sysfs与设备模型紧密集成，其目录结构直接映射设备模型的对象层次关系，为设备管理和调试提供了直观的接口。

设备属性通过sysfs文件系统向用户空间暴露。驱动程序可以使用DEVICE ATTR​或CLASS ATTR​宏定义属性文件，通过show​和store​函数实现读写操作。例如，LED驱动可以定义brightness​属性，用户可以通过echo 1 > /sys/class/leds/led0/brightness​来打开LED。

这里的目录只是给我们提供了如何去看整个设备模型的不同的视角，所有的设备都在 /sys/ devices/ 存放一份

路径 描述

/sys/class/ 把看问题的视角提高到了类别的高度

/sys/power/ 电源管理相关接口，支持系统挂起（suspend）、恢复（resume）等操作配置

设备类目录的创建过程如下：

  1. 创建设备类：使用class Create​函数创建一个设备类对象，指定类名称和所属模块。
  2. 创建类目录：class Create​会自动在/sys/class​下创建一个同名目录，用于组织同类设备。
  3. 创建设备节点：使用device Create​函数在类目录下创建设备节点，用户空间可以通过该节点访问设备属性。

sysfs中的属性文件会随着设备状态变化自动更新。内核通过sysfs Notify或sysfs Notify Dirent函数通知sysfs文件系统属性值已改变，用户空间读取属性文件时会得到最新值。这种动态更新机制使得用户空间可以实时监控设备状态。

设备模型的事件处理与电源管理

设备状态变化（如热插拔、电源状态改变）会通过sysfs通知用户空间，用户空间程序可以据此调整自身行为。

电源管理是设备模型的重要功能之一。每个设备和驱动都可以定义电源管理操作（如suspend和resume函数），内核在系统进入休眠状态时，会自动调用这些函数，确保设备正确进入低功耗模式。电源管理操作通过struct dev_pm_ops结构体定义，包含设备的电源管理函数指针。

设备模型还支持设备树（Device Tree） ，这是一种描述硬件设备及其关系的数据结构，使得内核可以在运行时动态构建设备模型。设备树允许在不修改内核的情况下描述硬件配置，提高了系统的可移植性。在嵌入式系统中，设备树广泛用于描述SoC上的外设连接和配置。
